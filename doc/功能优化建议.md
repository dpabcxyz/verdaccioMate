## 二、P0：建议优先落地的三项

### 2.1 清理低版本：从「规则」升级为「规则 + 证据」

**现状**：清理逻辑为「保留最新 N 版，删除其余」。
**问题**：N 设大了占空间，设小了可能误删被锁版本引用的老包；且没有任何信号区分「真在用」与「真冷门」。

**关键事实约束（已核对代码确认）**：

- 原版 Verdaccio 缓存包**不体现依赖关系**：
  - 扫描器 `backend/scanner.js` 对每个 `${包目录}/package.json` 仅解析 `description / homepage / repository / author / license` 与 `versions/time`，从未读取 `dependencies` 字段；
  - 声明依赖（该包依赖谁）虽藏在 `meta.versions[v].dependencies` 中，但多为范围（`^1.2.0`）而非精确锁定，参考价值有限；
  - **被引用关系（谁锁定了哪个版本）在 verdaccio 缓存中根本不存在**——那是消费方工程 `package-lock.json` / `pnpm-lock.yaml` 的数据，不在 Registry 侧。
  - 结论：**放弃依赖解析路径**，改用 原版 Verdaccio 侧真实存在的数据近似「冷门」。

**建议方案**（用 Registry 侧证据近似冷门）：

| 信号 | 来源 | 判定 |
| --- | --- | --- |
| 最近访问时间 | verdaccio 访问日志（`GET /@scope/pkg/-/pkg-x.y.z.tgz`） | 非最新 N 版 **且** 最近 N 天零访问 → 冷门候选 |
| 版本发布时间 | 扫描已解析的 `versionsDetail[].date` | 发布于 N 个月前且不在最新 N 版 → 降级删除优先级 |
| 版本增长停滞 | 多次扫描快照对比 | 版本数长期无增长的包 → 订阅方大概率已锁版本，删除优先级低 |

**产出形态**：清理弹窗中选择规则后，列出「将删除的冷门版本」清单 + 依据（最后访问时间 / 发布日期），确认后才执行。

### 2.2 破坏性操作：软删除 / 回收站 + 批次回滚

**现状**：清理 / 删除是**真删除**，无回收机制。
**风险**：npm 包重新拉取要再走公网（跨境 + 限速），误删代价高。

**建议方案**：

1. 删除时先 `rename` 到 `storage/.trash/<pkg>/<version>`（同盘 rename，瞬时完成）；
2. `.trash` 保留 N 天（可配置），超期由每日定时任务自动物理清除；
3. 配合现有操作日志 `batchId`，实现**按批次回滚**：操作日志中删除类记录标记「可回滚」，一键从 `.trash` 移回原位；
4. 前端删除成功后 toast 提示「已移入回收站，可在操作日志中回滚」。

**收益**：把「最高风险操作」变成「可反悔操作」，是当前性价比最高的一项。

### 2.3 批量拉取失败：一键重试闭环

**现状**：`sync-latest` / Top200 拉取有逐包进度 + 失败明细，但失败后无「按失败列表重试」入口，处理需手工。

**建议方案**：失败明细旁增加「重试失败项」按钮，后端接口接收失败的包名列表（或 batchId 关联的失败记录）重新入队；重试策略沿用现有并发控制，避免打爆外网。

## 三、P1：治理深度与协同放大

### 3.1 磁盘占用分布可视化

- **现状**：只能看到总包数 / 总字节，无法回答「谁吃掉了 80% 空间」。
- **建议**：
  - 版本栈折叠：每包展示「版本数 + 单版本占用」，按版本栈聚合得出「冗余空间」= 非最新 N 版占用合计；
  - Scope 分布：按 `@scope` 聚合占用占比；
  - Top 占用 TOP20 排行（包名 / 版本数 / 占用 / 建议清理空间）。
- **价值**：让「清理哪些包」的决策有直观依据。

### 3.2 扫描历史留存与增长趋势

- **现状**：每次扫描覆盖快照，不保留历史，无法度量治理效果。
- **建议**：SQLite 已有，新增一张 `scan_history(scan_id, scanned_at, pkg_count, total_bytes)` 表；定时扫描落一行。
- **产出**：概览页磁盘增长曲线（周 / 月）；「近 30 天清理回收 XX GB」统计卡片——治理工具最有说服力的成果证明。

### 3.3 消息通知的团队出口

- **现状**：消息中心为站内信 + 30s 轮询，只触达「打开 Verdaccio Mate 的人」。
- **建议**：站内信基础上增加**出站渠道**，预警 / 批量拉取结果 / 榜单变化可推送至：
  - 企业微信机器人 Webhook（最简单）；
  - 飞书机器人 Webhook；
  - SMTP 邮件（低频摘要）。
- **注意**：30s 轮询可保持（内网轻量），不需上 WebSocket；出站渠道采用「失败静默 + 日志记录」策略，不影响主流程。

### 3.4 只读角色

- **现状**：单账号（admin + 固定密码），登录鉴权 + 限流已有。
- **建议**：用户表加 `role` 字段（admin / viewer）；viewer 可看扫描结果、预警、榜单、日志，不可执行删除 / 清理 / 拉取等写操作（后端接口层校验）。让 Verdaccio Mate 可安全共享给团队查看。

## 五、前置事实：原版 Verdaccio 访问日志获取方案

> 说明：本方案是 P0「冷门版本」建议的数据基础，因涉及外部设施（verdaccio 配置），单独成节。

### 5.1 日志在哪里

| 配置方式 | 输出位置 | 获取方式 |
| --- | --- | --- |
| 默认（`{ type: stdout, level: http }`） | 容器标准输出 | `docker logs <容器名>`（compose 为 `docker compose logs verdaccio`） |
| 显式 file 配置 | 指定路径日志文件 | 读文件；配合 volume 挂载持久化 |
| 前置 nginx 反代 | nginx access.log | 同样记录 `/@scope/pkg/-/pkg-x.y.z.tgz` 请求 |

verdaccio 默认日志级别即 `http`，tarball 下载请求逐条记录，形如：

```
http <-- GET /lodash/-/lodash-4.17.21.tgz (200) 14ms
```

`/-/lodash-4.17.21.tgz` 即「有人拉取了 lodash 4.17.21」的可靠证据。

### 5.2 推荐配置（file 日志）

verdaccio `config.yaml`（Docker 镜像内 `/verdaccio/conf/config.yaml`）：

```yaml
logs:
  - { type: stdout, format: pretty, level: http }
  - { type: file, path: /verdaccio/storage/verdaccio-http.log, format: pretty, level: http }
```

storage 目录已通过 volume 挂载（Verdaccio Mate 扫描的就是该目录），日志文件将和缓存数据同盘，宿主机路径对 Verdaccio Mate 可见。

### 5.3 Verdaccio Mate 侧解析方案

1. 匹配 `GET /(.+)/-/(.+-\d+\.\d+\.\d+\.tgz)`，拆出包名与版本；
2. 只统计 `(200)` 行，过滤 `(404)` / `(500)`；
3. 按天聚合入库 `{ 包名, 版本, last_seen, count }`；
4. 供清理决策使用：非最新 N 版 **且** 最近 N 天零访问 → 冷门候选。

### 5.4 注意的坑

- **日志轮转**：file 日志不自动按天切分，需 logrotate 或 Verdaccio Mate 按天截断；
- **stdout 不持久**：`docker logs` 重启容器可能丢，长期统计需切 file；
- **失败请求**：只统计 `(200)`，拉取失败的行不计入访问证据。
